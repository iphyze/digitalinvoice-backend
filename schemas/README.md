# NRS UBL v1.1 – local structure

This is a **DigitalInvoice local JSON Schema projection**, not an official exported NRS schema and not evidence of production certification.

- `nrs-ubl-v1.1-local.schema.json`: Draft 2020-12 structure used for offline validation tests.
- `NRS-UBL-FIELD-MAPPING.csv`: traceability from outgoing JSON to local DB columns.
- `../tests/generated_fixtures/`: six JSON examples **generated by executing `firsUblPayload`**, all with fictional identifiers/classification codes for unit testing only.

Schema fields: `business_id`, `irn`, `issue_date`, `invoice_type_code`, `invoice_kind`, `document_currency_code`, `tax_currency_code`, `accounting_supplier_party`, `accounting_customer_party`, `payment_means`, `allowance_charge`, `tax_total`/`tax_subtotal`, `legal_monetary_total`, `invoice_line`, `billing_reference` for credit notes.

**Amount rules:** DigitalInvoice persists decimal money to 2 d.p. In the adapter all totals and reconciliation are calculated in integer kobo before JSON encoding. The invoice-level discount appears as a negative `allowance_charge`, and line discounts reduce `invoice_line.line_extension_amount`. Tax subtotals aggregate persisted post-discount taxable amounts per tax category/rate. Rounding is inherited from the application's existing invoice calculation.

**Known limitation:** old invoices snapshot buyer name/TIN/street but not the new state/LGA/postal-zone codes; the adapter reads those codes from the current customer record. If customer data changes after issuance, an older invoice's address codes may not represent the original transaction. Snapshot these codes at invoice approval in the later Step 3 catalogue/data model extension before production submission.

**References checked:**

The NRS live `/validate` endpoint remains authoritative. No outbound HTTP request is implemented in this step.
